## 2. Правило 100%: як перевіряли

Спосіб перевірки: Суму кожного батьківського вузла другого рівня (`1.1`–`1.5`) перевірено арифметично як суму його листових пакетів, а корінь `1` — як суму `1.1`–`1.5` (`200+280+440+140+120 = 1180`). Додатково звірено кожен рядок із пунктами «Що робимо» статуту (ЛР5) та списком історій `REL-1` беклогу (ЛР6), щоб жоден пакет не дублювався у двох гілках.

Робота, яку ледь не забули: Налаштування контейнера й HTTPS-доступу на сервері академії (`1.5.1`) та підготовка короткої інструкції для викладачів двох кафедр (`1.5.2`) — цих задач не було в користувацьких історіях беклогу, але без них реліз не пройде погодження з `ST-05` і не запуститься на іншій кафедрі.

Що свідомо поза обсягом:

- Власні акаунти користувачів, система логінів і відновлення паролів — суперечить вимозі «без реєстрації» і не вміщується в 14 тижнів.
- Двостороння live-інтеграція через API з Jira / Linear / Trello — не вміщується в ліміт одного `Dev 100%`, замість неї реалізується CSV-експорт (`1.3.3`).
- Нативні мобільні застосунки під iOS та Android — обмежуємось адаптивним веб-інтерфейсом у браузері (`1.2.2`).

## 4. Критичний шлях

Дата старту робіт: **2026-11-30**. Тиждень це п'ять робочих днів, свята не рахуємо.

| Що | Значення |
| --- | --- |
| Критичний шлях, робочих днів | 117 |
| Ланцюг критичних робіт | T-02 → T-05 → T-06 → T-07 → T-08 → T-10 → T-11 → T-14 |
| Дата завершення за планом | 2027-05-12 |
| Строк мого варіанта, робочих днів | 70 |
| Різниця | +47 робочих днів |

Чи вкладаємось: **ні** (за чисто послідовним ланцюгом аналізу, розробки і тестування критичний шлях становить 117 робочих днів проти ліміту 70 робочих днів).

Що з цим робимо: Фіксуємо **дату релізу `2027-03-08`** (70 робочих днів за V05) і скорочуємо критичний шлях двома кроками: 1) переводимо `T-06` у паралельний старт після перших 5 днів `T-02` (узгодження базових вимог входу без очікування повної специфікації CSV), що знімає **30 днів**; 2) відсікаємо з `REL-1` обидві `could`-історії (`S-05`, `S-15`) і проводимо тестування `T-10` інкрементально в межах спринтів паралельно з `T-07`/`T-08`, скорочуючи фінальний цикл `T-10 + T-11` на **17 днів**. Ціна рішення — менший обсяг першого релізу та вищий ризик дрібних переробок через ранній старт `T-06` до фіналізації всіх деталей аналізу.

Робота з найбільшим резервом: `T-01` і `T-13` (по **67 днів** резерву), бо управлінські процеси `PM` (`1.1.1`, `1.1.2`) ідуть паралельно з основним ланцюгом аналізу, розробки та тестування.
